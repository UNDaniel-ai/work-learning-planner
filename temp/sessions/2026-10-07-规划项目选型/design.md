## 2. Scope Decomposition

这个项目实际上包含三个相互关联、但可以分阶段交付的子系统：

1. **任务执行层**
   - 项目、任务、子任务、截止时间、重复规则、提醒和基础视图。
   - 首选由 Vikunja 提供。
2. **个人规划层**
   - 工作 / 学习领域、目标、学习主题、周计划、时间块和复盘。
   - 由本项目负责，这是主要差异化。
3. **反馈与优化层**
   - 完成情况、时间投入、计划偏差和周复盘。
   - 第一版只做可解释的基础统计，不做复杂评分或 AI 自动规划。

如果把三个子系统一次性做完，范围会膨胀成一个新的项目管理平台。因此第一版只交付“个人规划层与任务执行层之间的最小闭环”。

## 3. 目标与非目标

### 目标

- 能把工作和学习分成两个可识别的领域。
- 能把目标关联到项目和执行任务。
- 能在周视图中选择本周重点，并落到每天要做的任务。
- 能记录时间块或专注时段。
- 能在每天和每周结束时留下复盘。
- 能导出自己的规划数据，避免被单一服务锁定。
- 重要行为可测试，重要决策可在 Git 中追溯。

### 第一版非目标

- 团队协作、角色、权限和组织管理。
- 财务、健康、社交等完整 Life OS 模块。
- 自己实现成熟的提醒、重复任务、日历同步和看板引擎。
- 第一版就做 AI 自动排程。
- 为了追求全平台而同时维护桌面端、移动原生端和 Web 端。

## 4. 方案比较

### 方案 A：Vikunja Companion，推荐

独立开发一个个人规划 Web 应用，通过 Vikunja API 读取和写入执行任务。本项目只保存目标、学习主题、时间块、复盘和同步映射等差异化数据。

优点：

- 复用 Vikunja 的任务层级、截止时间、重复任务、提醒、过滤器和基础视图。
- Vikunja 有 API 与 OpenAPI 文档，且 API v2 是当前推荐方向；可以把任务提供者抽象成适配器。
- 不需要 fork Vikunja，也不需要维护上游 UI。
- 规划层可以独立演进，未来可以替换成其他任务提供者。
- 可以先做单用户、单实例和本地配置，控制首版复杂度。

缺点：

- 存在两套数据：Vikunja 任务数据和本项目规划数据。
- 需要处理外部任务 ID、同步失败和版本兼容。
- 需要用户先运行一个 Vikunja 实例，或提供一个可连接的 Vikunja 服务。

主要风险：

- 如果一开始做双向实时同步，会迅速进入冲突解决和离线同步问题。
- Vikunja API 的版本、部署地址和认证方式需要在适配器层隔离。
- 如果后续把 Vikunja 修改版打包或对外提供，需要单独核查 AGPL 义务。

成本判断：中等。主要成本在规划层和同步边界，而不是任务基础设施。

### 方案 B：Super Productivity 插件或外部面板

把 Super Productivity 当作主要执行应用，通过插件 API 或本地 REST API 增加目标、学习和复盘入口。

优点：

- 时间盒、专注计时、时间记录和任务执行体验成熟。
- 适合快速验证“每天如何执行”的工作流。
- 不需要自己重新做任务、计时和桌面交互。

缺点：

- 产品形态受桌面应用限制，难以自然覆盖 Web、移动端和自托管服务。
- 插件 API 适合扩展行为，不适合承载一个完整的个人规划数据模型。
- 本地 REST API 是桌面端能力，无法天然成为长期 Web 后端。
- 如果直接 fork 核心应用，升级和维护成本会快速上升。

主要风险：

- 规划数据与执行数据的所有权边界不清。
- 过度依赖特定客户端，后续迁移成本高。

成本判断：低到中等。适合做验证工具或执行层，不适合做本项目的长期架构核心。

### 方案 C：从零构建一体化系统

自己实现任务、目标、日历、时间记录、提醒、复盘、同步和全平台体验。

优点：

- 数据模型和交互完全由本项目控制。
- 没有外部底座版本、许可证和 API 兼容约束。
- 长期可以形成一个真正统一的产品。

缺点：

- 需要重做大量已经成熟且容易被低估的基础能力。
- 首个可用版本会被认证、提醒、重复规则、备份和同步拖慢。
- 个人规划方法还没有经过真实使用验证，过早固化模型风险很高。

主要风险：

- 可能花很久实现“能用”，却没有验证“好用”。
- 数据迁移和长期维护全部由本项目承担。

成本判断：高。除非方案 A 经过真实使用后证明无法表达核心工作流，否则不选择。

### 方案结论

| 维度 | 方案 A：Vikunja Companion | 方案 B：Super Productivity 扩展 | 方案 C：从零构建 |
| --- | --- | --- | --- |
| 快速验证执行 | 中 | 高 | 低 |
| 目标 / 学习 / 复盘适配 | 高 | 中 | 高 |
| 自托管与数据掌控 | 高 | 中 | 高 |
| 移动 / Web 可扩展性 | 高 | 低到中 | 高 |
| 通用基础设施成本 | 中 | 低 | 高 |
| 长期迁移能力 | 高 | 低到中 | 高 |
| 首版综合风险 | 中 | 中 | 高 |

**推荐方案：A，Vikunja Companion。**

方案 B 保留为真实工作流验证工具，方案 C 保留为未来在外部底座不够用时的迁移方向。

## 5. 推荐架构

### 架构原则

1. **外部任务底座负责执行事实**
   - 任务是否存在、是否完成、截止时间和重复规则以 Vikunja 为准。
2. **本项目负责规划语义**
   - 目标、学习主题、周计划、时间块和复盘属于本项目。
3. **第一版避免实时双向同步**
   - 先采用显式刷新、幂等写入和同步映射。
   - Webhook、离线队列和冲突解决延后。
4. **提供者可替换**
   - 通过 `TaskProvider` 接口隔离 Vikunja。
   - 测试默认使用内存假提供者，不依赖外部服务。
5. **本地数据可导出**
   - 本项目的规划数据可以导出为 JSON。
   - 外部任务数据仍可通过 Vikunja API 或其导出能力取回。

### 推荐的数据边界

本项目本地保存：

- `area`：工作、学习等领域。
- `goal`：季度 / 月度 / 周目标。
- `learning_topic`：课程、技能、阅读主题或训练主题。
- `planning_period`：周计划和日计划。
- `time_block`：预留的专注时段或实际投入时段。
- `review`：每日 / 每周复盘内容和少量结构化字段。
- `task_link`：本地语义对象与 Vikunja 项目 / 任务的映射。
- `sync_cursor`：同步状态和最后一次成功读取信息。

Vikunja 保存：

- 项目、子项目、任务、子任务。
- 截止时间、优先级、重复规则、提醒、标签和完成状态。
- 任务描述、附件和任务级协作信息。

首版不把 Vikunja 的每个字段复制到本地数据库。需要展示时从 API 读取，需要关联时只保存外部 ID 和少量快照。

## 6. 数据流

### 创建规划任务

```text
用户选择目标 / 学习主题
  -> 输入任务标题和计划日期
  -> Planner 创建或更新 Vikunja task
  -> 保存 task_link
  -> 页面显示外部任务状态
```

### 周计划

```text
读取本地目标和学习主题
  -> 读取 Vikunja 未完成任务
  -> 用户选择本周重点
  -> 保存 planning_period 与 time_block
  -> 生成 Today 视图
```

### 每周复盘

```text
读取本周计划、任务完成状态和时间块
  -> 用户记录完成情况、偏差和下周调整
  -> 保存 review
  -> 只生成可解释的摘要，不自动修改下周计划
```

## 7. MVP 页面与用户工作流

### 页面

1. **Today**
   - 今日时间块。
   - 今日重点任务。
   - 工作 / 学习切换。
   - 快速完成、延期和记录实际投入。
2. **Weekly Plan**
   - 本周目标。
   - 工作与学习的任务分配。
   - 计划投入时间和已完成时间。
3. **Goals & Learning**
   - 目标列表。
   - 学习主题与当前进度。
   - 关联的 Vikunja 项目或任务。
4. **Review**
   - 每日 / 每周复盘。
   - 计划与实际的差异。
   - 下周只记录调整建议，不做黑盒自动安排。
5. **Settings**
   - Vikunja 地址和连接状态。
   - 认证令牌本地保存方式。
   - 导出、导入和备份。

### 第一条完整工作流

```text
创建一个工作目标
  -> 创建一个学习主题
  -> 从 Vikunja 导入或创建任务
  -> 放入本周计划
  -> 分配一个时间块
  -> 完成任务
  -> 周末记录复盘
```

如果这条链路不能在一周真实使用中带来帮助，继续增加模块没有意义。

## 8. 同步、备份与安全

### 同步策略

第一版采用：

- 页面进入时读取 Vikunja。
- 用户显式刷新。
- 写入操作使用幂等请求。
- 保存外部 ID，不依赖任务标题匹配。
- 同步失败时保留本地操作意图和错误信息，不静默丢弃。

后续再评估：

- Vikunja webhook。
- 后台同步队列。
- 离线编辑。
- 冲突解决。

### 备份策略

- 本项目规划数据提供 JSON 导出。
- 数据库迁移必须可逆或提供备份前置检查。
- Vikunja 数据依赖其自身备份。
- 令牌和 `.env` 文件永不提交到 Git。

### 安全边界

- 单用户首版可以使用本地配置，不引入组织级权限。
- 令牌只在服务端或本地安全存储中使用，不写入日志。
- 外部任务内容进入页面时按纯文本 / Markdown 规则渲染，避免直接执行 HTML。
- 对外部署前再增加登录、CSRF、限流和审计。

## 9. 设计挑战

### 挑战一：为什么不直接 fork Vikunja

Vikunja 的任务能力成熟，但本项目的差异化不在任务 CRUD，而在目标、学习主题、周计划和复盘。直接 fork 会让我们承担上游合并、前端定制和发布维护。独立 companion 更容易保持上游可升级。

### 挑战二：为什么不把所有数据都复制到本地

复制任务全量字段会产生第二个任务系统，带来同步冲突和数据漂移。首版只保存规划语义和外部 ID，任务事实以 Vikunja 为准。

### 挑战三：为什么不第一版就做自动排程

用户的真实精力、任务耗时和临时打断需要先通过真实使用获得数据。没有历史数据时的自动排程容易制造虚假的精确感。第一版先允许用户手动规划并记录偏差。

### 挑战四：为什么不把学习笔记也塞进第一版

学习笔记属于知识管理边界，和任务执行的存储、检索与编辑模型不同。第一版只保存学习主题、资源链接和复盘摘要；完整笔记保留给 Logseq、AppFlowy 或未来独立模块。

## 10. 可回滚与兼容策略

- 第一版不修改 Vikunja 数据结构。
- 所有外部写入都通过适配器，适配器可以切换为只读模式。
- 本地规划数据和外部任务 ID 分离，未来可以迁移到其他任务提供者。
- 为 `TaskProvider` 保留内存实现，单元测试不依赖 Vikunja。
- 只支持一个明确的 Vikunja API 版本，连接时检查版本并提示不兼容。
- 若同步发生异常，可以停止写入，保留本地规划数据和导出文件。

## 11. 验证策略

设计进入实现计划后，至少需要这些验证：

- 领域规则测试：目标、周计划、时间块和复盘状态转换。
- Provider contract tests：创建、更新、完成、延期和读取任务。
- 同步失败测试：网络失败、令牌过期、外部任务被删除。
- 数据导出 / 导入测试。
- 端到端测试：从创建目标到完成周复盘的一条完整路径。
- 一周真实使用验收：至少包含工作任务、学习任务、延期任务和一次周复盘。

## 12. 待确认事项

这些事项不阻塞本设计的推荐方向，但需要在实现计划前确认默认值：

1. 是否必须自托管 / 离线。默认：接受自托管，首版不承诺完全离线。
2. 是否需要移动端。默认：先做响应式 Web / PWA，不做原生 App。
3. 是否需要公开部署。默认：个人私有部署，不做多用户 SaaS。
4. Vikunja 是否由本项目自动启动。默认：先由用户单独部署，本项目通过环境变量连接。
5. 第一版是否包含时间记录。默认：包含手动时间块和实际投入，不做复杂自动追踪。

## 13. 设计结论

推荐在下一阶段实现：

```text
独立的 Work & Learning Planner Web 应用
  +
Vikunja API v2 任务适配器
  +
本地规划数据库
  +
JSON 导出和可回滚同步
```

第一实现切片应是“连接 Vikunja + 读取任务 + 建立一个周计划”，而不是先做完整仪表盘或完整 Life OS。
