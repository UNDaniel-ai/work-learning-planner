# 需求对齐与调研边界

## 用户目标

用户希望有一个项目来进行自己的工作与学习规划，希望先深度分析 GitHub 上是否存在可直接利用或适合二次开发的项目，再决定是否从零开发。

## 当前已知约束

- 目标对象是个人工作与学习规划，不是默认面向团队协作。
- 需要比较现成项目与从零开发的投入、收益和长期可维护性。
- 本轮先做 GitHub 事实调研与路线推荐，不开始产品编码。
- 项目必须使用 Git 追踪。
- 需求、调研、设计、实现步骤、进度、验收和后续优化记录都必须保存在项目仓库内。
- 后续每个重要阶段应留下可读的 Git 提交或里程碑。

## 待核实的核心能力

- 目标管理：年度 / 季度 / 月 / 周 / 日分层。
- 工作与学习的并行管理，以及不同类型任务的区分。
- 任务拆解、优先级、截止时间、重复任务和提醒。
- 日历、看板、列表、时间线等视图是否足够。
- 复盘、习惯、学习进度和长期目标之间的关联。
- 时间记录、专注计时或番茄钟是否需要。
- 数据导入导出、API、插件和二次开发能力。
- 本地优先、自托管、隐私和多设备同步。
- 移动端 / 桌面端 / Web 的实际可用性。

## 调研候选池（初始）

- Vikunja
- Super Productivity
- Plane
- OpenProject
- Planka
- AppFlowy
- Logseq

候选池不是最终名单，将根据 GitHub 当前维护状态、产品边界和与个人规划的匹配度增删。

## 需要用户后续确认的关键问题

1. 规划重心更接近“任务执行管理”、 “目标与复盘”，还是“知识库与学习记录”？
2. 是否需要自托管、离线和数据完全掌握？
3. 是否需要手机端，以及是否接受现成项目的界面与工作流妥协？
4. 是否有必须保留的工作系统或数据源，例如 GitHub、Jira、Notion、日历或企业微信？
5. 第一阶段更看重尽快可用，还是更看重做成高度贴合自己的长期系统？

## 验收标准（本轮研究）

- 至少核查 4 个真实 GitHub 项目的一手资料。
- 对每个候选给出定位、核心功能、技术与部署门槛、维护信号和主要风险。
- 明确指出哪些项目适合直接使用、哪些适合二次开发、哪些不值得作为底座。
- 给出“复用 / 二次开发 / 从零开发”的推荐路线及理由。
- 明确下一阶段需要用户确认的最小决策集合。

## GitHub 调研结果

核查日期：2026-10-07。GitHub 的 star、issue、commit 数会持续变化，以下数字只作为本次快照，不作为质量的唯一依据。

### A. 最适合直接使用的成熟项目

#### 1. Super Productivity

- 仓库：[super-productivity/super-productivity](https://github.com/super-productivity/super-productivity)
- 定位：个人任务执行、时间盒、时间记录和专注工具。
- 事实：仓库页面显示约 22.6k stars、22k+ commits，MIT 许可证；支持项目、子任务、标签、日程时间线、看板、艾森豪威尔矩阵、时间盒、工时统计、Pomodoro / Flowtime / 倒计时、多设备同步和多个 issue tracker 集成。
- 扩展能力：有插件 API；桌面版提供本地 REST API，可读写任务、项目、标签、重复任务和当前专注状态。
- 优点：直接解决“今天做什么、什么时候做、实际花了多久、如何保持专注”。
- 局限：它不是完整的目标管理或学习知识库；Web 和移动版存在能力差异；核心是较大的 Angular / Electron / Capacitor 应用，直接 fork 改造成本高。
- 判断：适合立刻使用，也适合作为“执行层”；不建议一开始 fork 核心代码。

#### 2. Vikunja

- 仓库：[go-vikunja/vikunja](https://github.com/go-vikunja/vikunja)
- 定位：自托管任务与项目管理系统。
- 事实：仓库页面显示约 5.6k stars、16k+ commits，AGPL-3.0-or-later；Go API 与 Vue 前端可打包为单一 binary 或 Docker 容器。
- 功能：项目与子项目层级、子任务、截止日期、重复任务、提醒、优先级、标签、过滤器、任务关系、附件、List / Gantt / Kanban / Table 视图、CalDAV、部分第三方任务导入。
- 扩展能力：有 API、Webhook、插件和开发文档，适合做外部个人规划层。
- 优点：数据掌控、自托管、模型清晰，适合建立“领域 / 目标 / 项目 / 任务”的层级。
- 局限：专注计时、时间盒、个人指标和学习复盘不是核心能力；移动端目前偏基础；自托管维护与备份需要自己负责；时间追踪等部分能力进入 Pro 体系。
- 判断：如果最终要做一个 Web 优先、自托管、可长期扩展的个人规划系统，它是最值得作为底座的候选。

### B. 能力强但不适合做个人底座的项目

#### 3. Plane

- 仓库：[makeplane/plane](https://github.com/makeplane/plane)
- 定位：Jira / Linear / Monday / ClickUp 替代品，面向团队和产品项目。
- 事实：仓库页面显示约 60.5k stars、7k+ commits，AGPL-3.0；支持 Docker 与 Kubernetes，技术栈包含 Django、React、PostgreSQL、Redis。
- 功能：Work Items、Cycles、Modules、Views、Pages、Analytics，以及团队项目管理语义。
- 判断：适合软件项目、团队协作、产品路线图，不适合个人工作学习规划。它的领域模型和部署复杂度都会把个人需求带偏。可作为团队项目管理参考，不建议作为本项目底座。

#### 4. OpenProject

- 仓库：[opf/openproject](https://github.com/opf/openproject)
- 定位：组织级项目与项目组合管理。
- 事实：仓库页面显示约 16.3k stars、115k+ commits，GPL-3.0；核心能力包括 portfolio、Agile / Kanban / Scrum、Roadmap、Gantt、时间追踪、成本与预算、缺陷管理。
- 判断：成熟度很高，但明显是企业级系统。个人使用的配置、学习成本和维护成本都过高，不建议作为个人规划项目的基础。

#### 5. AppFlowy

- 仓库：[AppFlowy-IO/AppFlowy](https://github.com/AppFlowy-IO/AppFlowy)
- 定位：Notion 类知识与协作工作区，带文档、Wiki、项目和 AI 能力。
- 事实：仓库页面显示约 77.2k stars、7k+ commits，AGPL-3.0；基于 Flutter 与 Rust，支持桌面、移动端和自托管。
- 判断：更适合“学习资料、笔记、知识库、文档协作”，不是高频任务执行和时间盒工具；代码体量与架构复杂度也不适合为了个人规划直接 fork。

#### 6. Logseq

- 仓库：[logseq/logseq](https://github.com/logseq/logseq)
- 定位：隐私优先的知识管理与本地优先笔记平台，支持 Markdown / Org-mode、任务和插件。
- 事实：仓库页面显示约 45.2k stars、25k+ commits；其 DB 版本和 RTC 同步在本次核查时仍标为 beta / alpha，并明确提示需要备份，可能存在数据丢失风险。
- 判断：非常适合学习笔记、每日记录、知识回顾和复盘；不适合作为唯一的任务执行系统。更适合作为 `Vikunja` 或 `Super Productivity` 的知识与复盘层。

#### 7. Planka

- 仓库：[plankanban/planka](https://github.com/plankanban/planka)
- 定位：自托管 Kanban 看板。
- 事实：仓库页面显示约 12.6k stars、1.2k commits；Community 版提供看板、列表、卡片、Markdown、附件、评论、自定义字段、计时器、截止日期、通知、Webhook 和 REST API，部分日历、时间线、重复任务等能力在 Pro。
- 判断：适合看板工作流，但缺少个人目标、学习记录、时间盒和复盘闭环。不作为本项目主底座。

### C. 与需求最接近但成熟度不足的个人项目

#### 8. Personal Execution OS

- 仓库：[Peter-McCann-Strain/Personal_Execution_OS](https://github.com/Peter-McCann-Strain/Personal_Execution_OS)
- 定位：单人、自托管的目标、项目、任务、习惯、复盘和知识工作区。
- 事实：README 明确把项目标为 public preview；仓库页面显示 12 commits、0 stars，Apache-2.0；采用 React PWA、FastAPI、PostgreSQL、Redis、后台 worker，并提供较完整的架构、安全和测试文档。
- 判断：产品思想与“工作 + 学习 + 复盘”最接近，适合借鉴信息架构；但公共验证信号太少，不应直接承载不可替代的个人数据。

#### 9. Planner

- 仓库：[rileybrown841/planner](https://github.com/rileybrown841/planner)
- 定位：单用户数字规划器，包含课程 / 学期、任务、日历、考试与项目倒计时、习惯、预算和 Pomodoro。
- 事实：README 声称九个阶段已完成；仓库页面显示 24 commits、0 stars、0 issues，技术栈为 Next.js 16 PWA + Supabase，部署依赖 Supabase 和 Vercel。
- 判断：和“工作 + 学习”场景直接匹配，适合快速看产品形态或作为短期原型参考；但仓库验证信号很弱，且把数据边界放在 Supabase，不适合作为默认长期底座。

#### 10. Life OS

- 仓库：[lunanoir21/Life-os-project](https://github.com/lunanoir21/Life-os-project)
- 定位：个人 Life OS，包含任务、习惯、日志、财务、目标、学习、日历和时间追踪。
- 事实：仓库页面显示 19 commits、约 6 stars，MIT；使用 Next.js 16、React、TypeScript、Rust / Axum、SQLite、Docker，前端与 Rust 后端分进程运行。
- 判断：功能面非常贴近“工作 + 学习 + 生活”一体化，但维护规模很小，架构比需求本身更复杂，适合借鉴功能拆分，不建议盲目作为生产底座。

## 初步结论

目前没有一个成熟项目同时把以下四件事做好：

1. 工作和学习的目标层级；
2. 日 / 周执行与时间盒；
3. 学习资料与过程记录；
4. 可持续的复盘与指标。

因此推荐采用“稳定执行底座 + 自己的薄规划层”：

- **首选路线：Vikunja + 自定义个人规划层**
  - Vikunja 负责任务、层级、截止时间、重复任务、提醒、过滤器和基础视图。
  - 我们自己的规划层只负责领域模型和差异化：目标、学习主题、周计划、时间块、每日 / 每周复盘、工作与学习指标。
  - 这样不是把成熟任务系统重新造一遍，而是把开发资源放在真正属于你的规划方法上。
- **最快可用路线：直接使用 Super Productivity**
  - 如果当前最重要的是马上开始执行和记录时间，先用它跑 1-2 周。
  - 再根据真实使用中的缺口决定做插件、做外部 dashboard，还是转到 Vikunja 底座。
- **不推荐首期路线：从零做全套**
  - 从零做任务、提醒、重复规则、日历、同步、权限、备份、移动端和统计，会把大量时间花在通用基础设施上。
  - 只有当我们已经通过真实使用验证“现成底座无法表达核心工作流”时，才值得从零构建。

## 当前假设与风险

- 当前把用户视为单人使用者，尚未确认是否需要团队协作。
- 当前默认重视数据掌控和长期可扩展性，尚未确认是否接受云端 Supabase / SaaS。
- 当前把“规划”理解为目标到任务再到复盘的闭环，而不是单纯 Todo List。
- 需要注意 AGPL 项目在对外提供修改版网络服务时的源码义务；如果只是个人私有使用，工程风险与公开商业化不同。
- 小型个人仓库的功能描述可能超前于实际稳定性，必须在决定采用前做本地安装、备份恢复、移动端和核心工作流验收。

## 建议的下一步

在进入设计阶段前，只需要确认四个决策：

1. 先用现成工具跑一轮，还是直接做自己的 Web 项目？
2. 如果自建，是否接受 `Vikunja` 作为任务底座？
3. 是否必须自托管 / 离线，还是接受 Supabase / 云同步？
4. 第一版是否只做“工作 + 学习 + 日周复盘”，暂时不做财务、健康、社交等 Life OS 模块？
